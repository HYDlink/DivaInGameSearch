# 搜索卡顿测量：先区分文字显示与结果更新

2026-11-01。用户确认问题包含输入框文字本身延迟。本轮保留已部署的300毫秒防抖作为固定基线，没有把调参当作卡顿修复。源码的防抖只作用于后台查询启动，输入框不刻意等待防抖。

## 在游戏里复现并记录

1. 保持发生问题的原生页面、搜索领域、角色和图片状态，打开搜索窗。
2. 点顶部“性能监测”，再点“开始15秒记录”。
3. 按平常方式逐字输入，复现文字迟出现。只需搜索，不必Enter定位。分别记录英文直接输入和实际使用的中文／日文IME；不同输入方式不要混成同一结论。
4. 15秒结束后再次打开“性能监测”，点“导出报告”。
5. 报告在本Mod目录的 `search-performance.tsv`，UTF-8，中文列名。每次导出覆盖这一文件，保留上一份时先复制它。

记录阶段只追加有界内存样本，不逐字符写磁盘、不记录查询文字。最多4096帧、128条已发布查询；达到上限可能提前结束。导出时才在后台格式化及写文件。测量期间不要附加Frida、D3D截图或调试断点；本轮自动采样已遵守，截图在记录前后单独进行。

## 怎样读数据

所有耗时都是单调时钟测得的同步历时，不等同于线程CPU占用或GPU执行时间。

| 数据列 | 回答的问题 | 不能据此推定 |
| --- | --- | --- |
| 输入锁等待 | Win32字符／IME消息进入本Mod后，等Host锁花了多久 | 操作系统、远程输入或IME在消息抵达之前的延迟 |
| 输入到绘制 | 最近一次字符／IME消息抵达，到本Mod该帧完成提交用了多久；-1表示本帧没有新消息 | 按下物理键到消息抵达的时间、显示器真正呈现时间；同帧多消息只记录最近一次 |
| 本Mod回调、帧锁等待 | DML OnFrame自身及获取Host锁耗时 | 游戏或其他Mod全部耗时 |
| 查询轮询、资源同步、界面构建、DX11提交 | 本Mod同步帧工作停在哪一段 | GPU独立执行及驱动／合成器完整耗时 |
| 纹理上传、上传张数 | 可见服装图片缓存未命中时，本帧同步创建纹理耗时 | 后台解包／解码的独立CPU占用；上传是界面构建的子项，不能重复相加 |
| 共享路由Hook | 原外层／选曲／状态函数执行后，本Mod路由与动作逻辑的同步耗时 | 被保留的游戏原函数耗时及所有其他Hook |
| 帧间隔 | 两次本Mod回调之间的间隔 | 单凭间隔减去本Mod耗时，不能把差值归咎给游戏或其他Mod |
| 输入到提交（含防抖） | UI条件改变到任务提交的总时间 | 输入框文字显示延迟 |
| 截止后调度等待 | 防抖截止后，多久才提交查询；旧future仍在运行等情形会落在这里 | 一定是共享worker排队；还可能是帧调度迟到 |
| 后台排队、查询执行 | 任务提交到worker开始、worker真正运行搜索的各段时间 | 已丢弃旧修订的完整工作量，报告仅收录已发布查询 |
| 完成到发布、发布应用耗时 | 搜索做完后等UI发布多久，应用结果本身花多久 | 输入消息抵达前的问题 |

若文字本身迟出现，先看输入锁、输入到绘制、帧间隔与同步绘制阶段；不要再靠更改防抖推断原因。若这些都低但用户仍能复现，就需要操作系统消息队列／IME／呈现链的外部跟踪，不能据此宣称没有卡顿。

## 必要时进一步用系统跟踪

本机已存在Windows Performance Recorder及Windows Performance Analyzer，`wpr -profiles`可列出GeneralProfile、CPU、GPU、DesktopComposition等。当前助手进程执行 `wpr -status` 返回权限不足0x80070514，没有启动系统记录。无需安装新工具，也没有修改系统权限。

如需追踪本Mod消息收到之前或GPU／呈现链的停顿，可在管理员PowerShell手动运行以下命令，复现约15秒再停止。输出必须留在本项目artifacts；ETL可能包含本机进程与文件活动，不自动上传。

```powershell
wpr -start GeneralProfile -start GPU -filemode
# 在游戏中复现文字迟出现，约15秒。
wpr -stop 'D:\Work\Projects\VibeCoding\DivaResearcher\DivaInGameSearch\artifacts\search-input-stall.etl'
```

用WPA打开ETL，按同一时间段查看CPU Usage、线程等待、磁盘及GPU活动。只有能把用户卡顿时段和具体线程／阶段对齐，才能据此决定修改哪条路径；若要细到C++函数，还需给对应构建生成并保留符号，不能只凭模块总CPU占用归因。
