# 共通 A／B／C 配置动作

日期：2026-11-15。沿用当前版本号。本文区分静态核查、隔离回归和实际游戏验收。

## 原因与原生路径

模型动作曾在装备读取、上下文认证、请求提交和预览接续中硬性要求范围为 Song=3。发型／道具的保存读取、动作、预览退出和卸除也有相同限制。定位器却一直接受范围0～3，因此会出现「能定位，但不能预览和换装」。

原生配置获取器 RVA `0x1D5E30` 并非只处理单曲：其共通分支按存档对象 `+0x169410` 的范围值0～2，选择 `save+0x168D68+scope*0x238+slot*0x1C` 的独立记录。来源700／701及游戏特殊模式有其他分支，产品不自行复刻这些分支，仍调用游戏原获取器并保留既有Mod链。

RVA `0x681CE0` 的自然提交路径先检查 `controller+0x10`：存在独立覆盖表时按槽位取记录，不存在时调用上述获取器。RVA `0x681A90` 的自然范围切换按0、1、2、3循环。地址、槽位记录大小和范围偏移统一声明于 `src/native_layout.h`，自拟名称已注明来源。

本轮通过已有本地 Ghidra 12.2 数据库只读反编译这四个函数，输出保存在忽略目录 `artifacts/scope-investigation/common-config-console.log`。REA MCP 的 Ghidra提供器未配置，本轮该部分使用已有本机Ghidra，不伪造REA Evidence ID。分析数据库只读打开并丢弃脚本临时修改，没有执行游戏函数。

## 产品修复

- `native_customization_config.h` 共用读取器按当前范围、来源和槽位取得独立记录；存档范围须与快照一致，不使用临时显示当作装备。
- 控制器独立覆盖表优先；播放列表缺少该表时仍拒绝回退，避免读取另一份配置。
- 模型能力、请求提交和预览接续接受共通 A／B／C 及单曲，原生更换和退出流程保持原有入口。
- 发型、四部位道具的装备读取、预览、更换、预览退出和卸除同步支持共通范围。
- 未知范围保持 Unknown，不再冒充共通；切换 A／B／C／单曲、槽位或外层上下文后取消旧事务。
- 拥有状态、列表唯一性、加载状态、独立装备读回及其他槽位保护继续执行。没有直接写装备ID或调用保存入口。

## 验证

Windows MSVC Release 构建通过，23／23 项CTest通过（包含工作树同时存在的其他改动）。其中本修复新增／扩展：

- `CustomizationConfigCheck`：139项断言，四范围六槽、覆盖表优先、播放列表无记录拒绝回退、未知范围、非法槽位和单曲来源检查。
- `ModuleActionCheck`：四范围336组跨人物预览／换装的能力、提交、执行与分类恢复；另覆盖六槽位独立读取、预览接续和切换范围取消。
- `CustomizationItemLocatorCheck`：总630项断言，新增四范围×发型／四部位道具的更换、预览退出、卸除与范围改变取消。

完整 `scripts/verify.ps1` 通过：实际DLL装载、五个导出、DX11初始化、33帧回调、输入协议及共用WARP预览。以上都不是新DLL在游戏内换装成功的证据。

本轮另做一次仅内存读取的Frida采样；游戏当时已在主页，读取到A/B/C独立保存表，随后卸载脚本并分离，没有输入、Hook或原生函数调用。它不能替代模型页面的范围切换对照，不能证明新DLL的动作链已经实机通过。

尚待实机验收：新DLL下A/B/C各自的模型预览／换装、发型和四部位道具动作、其他槽位及范围不受影响、预览退出恢复、保存后重新进入／重启的持久性。验收须保留操作前后截图并检查图片，配合独立保存记录读回。当前运行中的旧DLL不会因本地重新构建而更新。
