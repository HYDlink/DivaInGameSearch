# 服装名称在部分玩家电脑上显示日文：静态复查

日期：2026-11-15。源码基线：`3d2fe80`，版本 `1.2.5`。本次只做源码分析与隔离目录复现，没有修改产品实现、升版、部署、启动或附加游戏。

后续处理：用户随后授权修复并指定 1.2.6；已将官方名称基准与有效实体合并分离，加入保守的同一物品译名继承、候选解析回退和普通日志诊断。修复验收见 [ACCEPTANCE.md](../ACCEPTANCE.md) 的 1.2.6 记录。下文保留 1.2.5 调查时的源码位置和复现结果，不作为 1.2.6 当前实现描述。

## 结论与确定程度

**已确认当前版本存在漏修：服装定义被 Mod 覆盖后，官方中文名称转换会跳过这些条目。即使 Mod 提供的定义与官方内容完全相同，也会发生。** 这不要求 Mod 文件损坏，也不要求两个 DLL 的 Hook 发生冲突。

在直接重新编译的当前 `src/customization_catalog.cpp` 上，以完整、有效的中文和日文语言表为输入：无 Mod 时 30/30 个名称为中文；增加一份与官方内容完全相同的 Mod 普通服装表后，0/30 个名称为中文，零号名称变为截图中的 `初音ミク`。

用户补充：朋友应已安装最新版 1.2.5，且安装了不少 Mod。因此优先调查服装表覆盖，其次调查名称补丁覆盖、语言表选择与核验失败。**尚未取得朋友的来源诊断、有效 Mod 文件和实际加载 DLL 身份，不能指认某个具体 Mod，也不能将隔离复现写成他电脑上的实测结论。**

## 截图说明了什么

截图中的搜索标签、筛选项和角色名称均为中文；模型 ID 0、3、4、5、6 分别显示 `初音ミク`、`メイコスタイル`、`リンスタイル`、`スペチャン5`、`スペチャン39`。

已有本机审计 `artifacts/lang-audit/jp-after.tsv` 中这些编号的名称与截图相同；对应 `cn-final.tsv` 为“初音未来”“MEIKO风格”“铃风格”“太空频道5”“太空频道39”。因此截图符合“官方日文原名被保留或再次覆盖”的表现。它无法区分没有转换、转换失败与转换后被覆盖，也不能单凭截图证明某个 Mod 的存在。

这是一组可读的日文名称，并非普通乱码。不能以字体、系统区域或重新设置中文作为主要修复方向。当前 UI 绘制直接显示 `item.name`，不在绘制时重新判断名称语言。

## 一、最优先核对：Mod 定义导致官方译名资格丢失

代码链：

1. `MergeOfficialRegionTables`（`src/customization_catalog.cpp:123`）检查启用的 Mod 是否提供可读取的 `rom/gm_module_tbl.farc`。
2. 一旦存在，官方同逻辑实体表整表退出（第 141 行）。这是为避免恢复被 Mod 删除的 ID，本身有合理目的。
3. 后续普通表与追加表合并时，`Overlay`（第 96 行）以新定义整条替换旧定义，`definitionSource` 变为 `dml:...`。
4. 中文名称核验只统计 `definitionSource` 以 `official:` 开头的项目（第 344 行）；中文名称赋值也使用完全相同的来源限制（第 351 行）。
5. 因此，Mod 内原样保留的官方服装也被排除，名称保持实体定义中的日文。追加表只覆盖一个官方编号时，该编号也单独失去官方中文名。

现有来源贡献记录虽然可能保留被覆盖的官方来源，但名称转换不会据此恢复官方译名资格。普通 `rom/` 表触发官方整表退出时，原官方条目甚至不会先加入合并结果。

**这条分支早已存在；1.2.5 去掉 EXE 哈希判断后，它仍然存在。** 所以“主程序哈希已经不再限制”和“部分玩家仍显示日文”并不矛盾。

## 二、新核验规则依赖合并后的官方样本

第 348 行要求每种物品至少有 20 条官方原名，且与日文语言表的字符串逐字相等比例不低于 90%。模型与发型／道具分别核验。

- 中文表可读但日文基准表不存在时，中文名称仍不应用。
- 样本来自已被 Mod 覆盖后的集合。剩余官方样本少于 20 条，即使全部匹配也拒绝应用。
- 同一类样本不一致超过 10% 时，该类整体回退；名称中的标点、空白或版本差异也会影响逐字相等结果。

隔离用例中，30 条里覆盖 11 条，剩余 19/19 匹配仍导致全类回退。**这里的 11 是合成用例规模，不表示真实游戏只覆盖 11 件就必然导致整体回退**；真实门槛取决于剩余官方样本数量。

## 三、名称补丁可在成功转换后再次写回日文

第 375—386 行按 DML 来源优先级读取 `rom/lang2/mod_str_array.toml`：同一来源先 `cn.module.<ID>`，再通用 `module.<ID>`，首次写入决定显示名。高优先级来源的通用日文名可以覆盖官方中文名，也可以挡住低优先级来源的中文名。

隔离结果：官方核验 30/30 通过，仅添加 `module.0='初音ミク'`，零号仍变为日文。此时日志中的“官方定制语言表：cn”完全正常。

该优先级与已保存的 DML `StrArray.cpp` 中“同来源先语言分组后通用分组”的处理相符。不能一律禁止通用名覆盖，否则可能破坏作者明确命名的自定义服装；应先核对实际生效的名称来源。

还有一个兼容差异：参考 DML 同时读取平面字符串编号和 `module`／`customize` 分组，并在物品专用名称缺失时回退平面字符串。搜索当前仅一般支持分组名称，平面形式只有 X Song Pack 的特定 1272→997 特例（第 365—373 行）。隔离输入 `cn.275='中文服装0'` 没有被搜索应用。**在已经确认编号映射的条件下**，这可以解释某些中文补丁能改游戏本体名称，却没改到搜索名称；不能任意对所有 Mod 编号减 275。

## 四、语言表候选选择仍比较苛刻

`readStrings`（第 329—333 行）只接受与 `rom_steam/rom/lang2/<语言>/str_array.bin` **逐字相同**的内部路径，并立即返回首个候选的解析结果。

- 下层 `ReadEntriesInternal` 的后缀匹配不区分 ASCII 大小写并统一斜线（`src/module_assets.cpp:189,330`），上层却再次做原始字符串精确比较；两层规则不一致。
- 若环境实际使用其他内部前缀或路径大小写，即使枚举到候选也会被拒绝。隔离验证了这条条件，但没有证据表明朋友的归档确实使用不同路径。
- 首个精确路径候选解析失败时，不继续尝试后续有效的同名候选。CPK 列表按文件路径排序，不是按游戏实际挂载优先级选择。
- 这里只从 CPK 读取语言表，不直接解析 Mod 提供的完整松散 `str_array.bin`。不能假设磁盘快照与游戏最终挂载内容必然一致。
- `ReadCustomizationStrings` 拒绝整张含无效 UTF-8、越界偏移等问题的表；语言表损坏也可以触发原名回退。
- 日文核验只证明日文表与原名的偏移关系，未证明 `cn` 路径中的内容实际为中文。隔离输入中将中文候选内容换成日文后，核验仍通过，最终仍显示日文。

上述是条件成立时确定的程序行为，不能据此宣称其他发行版或朋友的文件损坏。

## 五、为什么普通日志不足以定位

1. 目录诊断中的“官方定制语言表：cn，有效字符串 N 条”只表示读取到字符串，不表示通过核验、覆盖了多少条，也不表示最终没有被名称补丁覆盖。隔离整表替换场景中，这句成功提示与“日文一致 0/0，不足”同时出现。
2. `CustomizationView::Poll` 接收目录后，不把 `catalog->diagnostics` 交给 `Log`。`mod.cpp` 的 `onCatalogChanged` 只发布人物映射。
3. 完整名称目录诊断实际位于“选项 → 来源诊断”（`src/customization_ui.cpp:689`）。普通 `search-diagnostics.log` 有初始化版本、游戏语言、输入与图片诊断，但缺少本次名称转换的详细诊断。图片资源日志不能代替名称目录日志。

朋友那里最少需要核对：

- 当前启动对应的 `search-diagnostics.log` 初始化版本行；若怀疑多份安装，再核对实际加载 DLL 的位置和身份，不能只看压缩包或配置里的版本号。
- 搜索模型 ID 0 并悬浮：来源显示哪个 Mod；“选项 → 所选项来源贡献”中有哪些定义与名称贡献。该面板不完整列出原始文件内容，需要结合下一项。
- “选项 → 来源诊断”中：是否有“官方同逻辑实体表整表退出”、相应“自动实体定义”、`官方模型语言表偏移核对` 的分子／分母，以及中日语言表读取失败提示。
- 命中来源提供的 `rom/gm_module_tbl.farc`、`rom/mod_gm_module_tbl.farc`、对应 `rom/lang2/mod_str_array.toml` 的存在情况和相关条目；不要求先删除所有 Mod。

若看到 **`0/0` + 官方整表退出 + ID 0 定义归某个 Mod**，就能把第一类问题落实到具体来源。若仍是官方定义且核验通过，则优先看名称补丁；若提示缺表或一致率不足，则转查语言表候选。

## 修复方向与边界

1. **先保存未受 Mod 合并影响的官方名称基准，再核验语言表。** 不要用合并后的剩余官方项目数量决定整个种类能否本地化。
2. **把定义来源与官方译名映射资格分开。** 对 Mod 中仍能确认为原官方物品的记录允许继承官方名称；真正新增、同 ID 重定义或显式改名的物品保留 Mod 语义。具体身份规则需结合原始角色、COS／对象等字段设计，不能只凭 ID 或原名相同就硬套中文。
3. 保留整表替换对实体集合的影响，不能为了恢复译名把 Mod 删除的官方条目重新加回来；也不能靠降低样本阈值或删掉 `official:` 条件盲目覆盖所有 Mod 名称。
4. 统一路径规范化，逐个解析候选；优先级和冲突要有可解释的选择规则，不能盲目接收任意平台同后缀表。
5. 平面名称仅在已认证的对应关系下兼容；保留作者有效的语言分组和通用名称优先级。
6. 目录发布时将语言、选中表来源、核验结果、官方译名实际应用数、Mod 覆盖数和回退数写入普通诊断日志。当前宽泛的“读取到 cn”不能作为修复验收条件。

本次完成原因调查与条件复现；具体朋友环境的触发来源仍待其来源诊断确认。本报告不宣称已经修复产品。
