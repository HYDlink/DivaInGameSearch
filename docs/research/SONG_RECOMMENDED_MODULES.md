# 按歌曲搜索推荐服装：运行时数据可行性

日期：2026-11-01。范围：调研与只读验证，不是新功能已经接入 DLL 的声明。

## 结论

**可以从正在运行的 MM+ 读取已加载歌曲的推荐服装元数据，不需要用户另外导出／维护一份「歌曲→服装」表，也不需要先把目标歌切到原生选曲菜单。** 本轮已经从实际游戏 PVDB 读取5首歌曲的名称、演出人物和 `pv_costume` 数组；接入搜索时可以直接复用现有歌曲检索引擎。

推荐数据与服装目录应分开：PVDB给出演出人物及服装COS编号，服装目录把 `(人物,COS)` 转成稳定 Module ID，再用现有卡片、图片、定位、预览／换装能力。这不是当前装备、玩家保存的曲目配置，也不是按歌名模糊猜衣服。

首选实现：**现有歌曲 Catalog/Search → 匹配 PVID → 运行时推荐快照 → 现有服装 Catalog → 推荐模型卡片。** 所有新增推荐缓存只在内存中生成，不要求用户操作解包器或提交额外资料。

## 当前构建可复用的读取路线

所有RVA相对当前主模块基址，仅对应上述已核查构建。堆指针和进程编号每次重新取得，不持久化使用。

| 对象或入口 | 当前结论 | 证据 |
| --- | --- | --- |
| `FindPVEntry`，RVA `0x4BC500` | 包装PVDB对象获取与按PVID查找；本轮只解码，不主动调用 | NewClassics声明＋静态＋运行时指令一致 |
| `0x4BBA20` | 获取PVDB静态对象；运行时是RIP相对LEA＋ret | 静态和指令读回 |
| `base+0x1753780` | 该获取器本轮返回的静态对象地址，不是需要解引用的全局对象指针 | 运行时LEA目标与静态一致 |
| 数据库 `+0x98/+0xA0` | 按PVID排序的PV对象指针表begin/end | 查找函数二分逻辑＋378条边界和样本读回 |
| PV对象 `+0x98/+0xA0` | 演出角色向量begin/end；不是上行的数据库对象 | 解析器、访问器及各歌曲1／6条读回 |
| 演出记录步长 `0x44` | 商业PC实际步长 | `0x4BEEE0` 静态乘除0x44，运行时边界吻合 |
| 演出记录 `+0/+4/+8` | type／原始人物／costume | 参考结构＋原始PVDB和多样本读回 |
| 演出记录 `+0xC+4*d` | 五项原生 `pv_costume` 零基值 | `0x4B0E10` 写入逻辑＋原始PVDB读回 |

重要修正：ReDIVA参考结构是0x40步长，商业PC为0x44。第一版保守探针对0x40边界明确拒绝，未当成可用数据；核对PC访问器后改为0x44才成功。不能将ReDIVA结构整块reinterpret_cast，也不能把记录 `+0x20` 的四字节原值当单一bool；本轮该位置有未解释数据，保留raw命名。

这里已能直接读取推荐原始值。完整生产解析还需核对特殊演出人物、缺省策略、难度／edition及多个定义的解析一致性。不能把读取原始值和整个商业PC“推荐”标记算法完全复现写成同一件事。

## 编号、人物及特殊情况

1. **COS不是Module ID。** 文本的 `pv_costume=115` 对应内部114；实体表 `COS_115`也按参考解析器转成114，再结合人物解析Module ID。不能把115或114直接作为模型搜索卡片的ID。
2. **一歌可能有多个推荐。** 637有6条，268有6条；其中包括GUEST或伪演出记录，不保证每条都等于一个可编辑歌者槽位。结果保存 `(PVID,performerIndex,原始角色类型,人物,COS,ModuleID)`；卡片可以去重，但不能丢掉对应角色及推荐理由。
3. **人物-1不等于推荐无效。** 268后五条type2对应参考源码的PSEUDO_SAME；需要遵循伪角色引用／继承规则，同时保留每条自己的推荐COS。不能全部当初音0，不能直接丢弃，也不能把前一条的整套服装复制过来。PC完整解析器行为需进一步交叉核对。
4. PVDB人物短token（如MIK/LUK/KAI）与服装表MIKU/LUKA/KAITO不是同字符串；原生人物编号也不能直接拿菜单分类编号代替。保持显式映射，参考既有module_category守卫。
5. **五个数组槽不等于UI的五个难度按钮。** ReDIVA原生枚举第4项是ENCORE，EX EXT由EXTREME和edition/extra表示；不要把本插件扁平难度4直接用于 `pv_costume[4]`。本轮样本全部五项相同，不能据此认证不同难度／edition关系。
6. 无推荐、未加载、未映射、目标资源缺失、多个实体同人物COS有歧义，分别保留状态。不能一律回退Module0并标成“推荐”。2D歌曲、特殊人物和Mod原始缺字段另测。
7. 推荐与拥有状态独立。能展示推荐不代表已拥有、可装备或适合当前玩家槽位；预览／换装沿用现有守卫，不因来自推荐结果放宽购买、人物、范围或槽位限制。

## 复用现有歌曲搜索

当前 `src/core.cpp` 的 `PrepareSong` 已生成原名、英文、可靠读音罗马音、假名／宽窄规范化和aliases的检索键；`Search(Catalog,Query,favorites)`承担PVID精确匹配、多词、来源、可用谱面和排序。`src/ui.cpp`调用这一实现，不能在服装模式重新用字符串contains做一个“差不多”的搜索。

建议在服装搜索页增加检索方式「模型名称／歌曲推荐」，保持同一搜索框：

1. 「模型名称」继续现有模型检索。
2. 「歌曲推荐」调用同一 `Search`，得到相同PVID及排序；共享同一歌曲Catalog和别名字典，保存独立查询条件，不改变歌曲页或游戏实际选中。
3. 若同名或多个歌曲命中，先显示精简歌曲候选并允许选择，再显示该曲推荐模型；不只悄悄采用第一首。可扩展为按命中歌曲分组，但不把重名歌混成一条推荐理由。
4. 对选中歌曲的推荐关系关联当前服装目录，复用真实图片和卡片。「推荐给：歌曲名 · 演出角色」与原有模型名、人物、ID并存。
5. 模型人物过滤不能无提示地把一首六角色歌曲只剩初音；可默认推荐视图展示所有关联人物，或明确显示“其他人物被当前筛选隐藏”。实际玩家人物／歌者槽位保持不变。
6. 搜索某歌的推荐模型仅改变搜索结果，**不会自动切到这首歌**。给当前曲／当前槽换装仍用动作时读到的上下文；推荐来源PVID只是解释信息，不能拿它替换动作请求的实际曲目身份。
7. 继续遵守“只有鼠标双击结果主体才能跨页”。输入歌名、选歌曲候选和读取推荐都不导航；推荐模型的预览／换装按钮不取得新的跨页权限。

## 两条不要求额外导出的实现路径

### 优先：读取已加载PVDB

游戏完成PVDB解析后，在安全生命周期边界把有界数据复制成插件拥有的不可变推荐快照；不让后台搜索线程访问游戏堆指针。曲库和Mod配置指纹变化、数据库重建、版本不支持时失效，未就绪时显示具体原因。

后台输入搜索沿用现有300毫秒调度和版本号，消费推荐快照与服装目录；不每个字符扫描全部游戏内存，也不每帧反复读取378条或解压CPK。查询结果保留kind/ID、原始人物及来源PVID。服装目录若反映更新后的磁盘配置而游戏尚未重启，不与旧运行时PVDB混称当前生效。

优势是拿到游戏实际加载的值，包括DML合并后的Mod覆盖；仍要核实后加载DLL／Mod是否会额外修正推荐及其生命周期。当前仅验证上述构建，未知版本不得盲读固定偏移。

### 备选：自动读取原始PVDB与CPK

已有 `ReadPvdb` 能读任意属性，但 `LoadCatalog` 转成 `Song` 时只保留歌曲检索／谱面需要的字段。当前发行 `data/base_pv_db.txt`、`dlc_pv_db.txt` 中未发现performer／pv_costume字段，因此不能声称“给Song加个字段就自动有全部推荐”。

如果选择文件路线，可利用现有CPK读取能力新增对基础／DLC完整PVDB的精确读取，再解析启用Mod的PVDB并核对DML合并规则，保留每个推荐字段来源；不要求用户额外导出。不能只读Mod的performer字段并把缺省视为基础无推荐，也不能把现有歌曲简化合并逻辑直接当成商业PC所有performer覆盖的认证。

这条路线兼容版本的成本可能较低，但它读取的是磁盘配置，未必等于当前进程已加载状态。两种来源必须可区分；不静默混用过期运行时、磁盘快照和手工名单。
